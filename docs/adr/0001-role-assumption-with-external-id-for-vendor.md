# ADR 0001: The fraud vendor assumes a role, protected by an external ID

**Status:** Accepted
**Context:** Fraudlytics' automated pipeline reads Nkosi's transaction data every day. Today it uses a long-lived access key for an IAM user in Nkosi's account. Fraudlytics serves many customers from one AWS account.

## Options considered

| Option | Verdict |
|---|---|
| Keep the IAM user and rotate its key | ❌ Still a long-lived secret held by a third party. Rotation is a process that fails silently |
| Bucket policy naming the vendor's account (resource-based access) | ❌ Workable for S3 alone, but Nkosi can't express the vendor's session limits or extend access beyond S3 in one place. Objects the vendor writes would be vendor-owned (see ADR 0003) |
| **Cross-account role + external ID** | ✅ Chosen |

## Decision

- Create `nkosi-fraud-vendor-access` in Nkosi's account. The trust policy names the vendor's **account** and requires `sts:ExternalId`.
- The permissions policy allows `s3:ListBucket` with an `s3:prefix` condition on `transactions/*`, and `s3:GetObject` on `transactions/*`. Nothing else.
- The external ID is generated by the vendor, unique per customer, and stored in Nkosi's trust policy.

## Consequences

- The vendor works with **temporary credentials** (one hour by default). There's no standing secret to leak.
- Revocation is one edit to one trust policy, in Nkosi's account, with no dependency on the vendor.
- The confused-deputy attack is closed. Trap A showed that no ID and another customer's ID are both refused.
- CloudTrail records `assumed-role/nkosi-fraud-vendor-access/<session-name>`. The session name identifies the vendor process, but the actor appears as Nkosi's role. If Nkosi needs per-person attribution inside the vendor, it should require `sts:SourceIdentity`.
- Access is scoped by prefix, so `internal/*` returned `403` to the vendor.
